# 语音日历工具 — 开发流程规范

> **用途**：规范从需求、设计、开发、验证到 PR 提交的完整任务流程。
> **适用范围**：语音日历工具网页端后续所有功能开发。
> **当前重点**：补齐“自然语言语音输入，自动解析并创建日历事件”的完整闭环。

---

## 一、开发原则

1. **每个 PR 只做一件事**
   - 一个 PR 只新增或修改一个明确功能。
   - 大功能必须拆成多个可独立运行、可独立验证的小 PR。

2. **主分支始终可运行**
   - 每次合并后，`main` 分支必须能安装、启动、构建。
   - 不允许把半成品功能直接合入 `main`。

3. **先闭环，再增强**
   - 优先完成用户能真实操作的最小闭环。
   - 对语音日历来说，优先级是：识别文本 -> 解析字段 -> 用户确认 -> 创建事件 -> 页面更新 -> 本地保存。

4. **文档与实现同步**
   - README 必须说明当前真实可用能力。
   - 未实现能力只能写在差距、计划或路线图中，不能写成功能承诺。

5. **验证先于提交**
   - 提交前必须运行对应检查命令。
   - PR 描述必须写清楚测试方式。

## 二、分支与提交规范

### 2.1 分支命名

统一使用：

```text
codex/<task-name>
```

示例：

```text
codex/add-requirements-doc
codex/voice-confirmation-flow
codex/local-storage-events
codex/browser-reminders
```

### 2.2 Commit 规范

提交信息保持短句，说明本次提交做了什么：

```text
Add voice calendar requirements document
Add command confirmation panel
Persist calendar events locally
Add browser reminder scheduler
```

### 2.3 PR 标题规范

```text
[codex] <一句话说明新增/修改了什么>
```

示例：

```text
[codex] Add command confirmation panel
```

### 2.4 PR 描述模板

```md
## 标题
一句话说明本 PR 新增或修改了什么。

## 功能描述
说明该功能的作用、用户如何使用、解决了什么问题。

## 实现思路
说明核心技术选型、主要文件变更、关键逻辑。

## 测试方式
- 运行了哪些命令。
- 如何手动验证功能正常。
- 如果有未覆盖风险，也要写清楚。
```

## 三、标准任务流程

每个功能都按以下步骤推进。

### Step 1：确认需求边界

输入：
- 需求说明书：[语音日历工具_需求说明书.md](./语音日历工具_需求说明书.md)
- README 当前能力说明：[README.md](../README.md)
- 当前代码实现

必须确认：
- 这个任务属于 P0、P1 还是 P2。
- 这个任务是否能单独成 PR。
- 是否会影响已有演示流程。
- 是否需要更新 README。

输出：
- 一句话任务目标。
- 明确不做什么。

示例：

```text
目标：实现语音识别后的解析确认卡片。
不做：不接入 DeepSeek，不实现提醒，不实现编辑事件。
```

### Step 2：拆分实现单元

每个任务需要先列出文件职责。

示例：

```text
lib/voice-parser.ts
- 负责把自然语言文本解析成结构化命令。

components/command-confirmation.tsx
- 负责展示解析结果，允许用户确认、取消和手动编辑。

components/voice-calendar.tsx
- 负责串联语音识别、解析、确认、事件写入和视图更新。
```

拆分原则：
- 解析逻辑不写进 UI 组件。
- 存储逻辑不写进语音组件。
- UI 组件只负责展示和交互。

### Step 3：先写验证点

每个任务至少要有一种验证方式。

推荐顺序：

1. 纯函数逻辑：优先写单元测试。
2. UI 行为：写手动验证步骤，必要时补组件测试。
3. 构建质量：运行 TypeScript 和 Next build。

当前项目最低验证命令：

```bash
corepack pnpm install --ignore-scripts
.\node_modules\.bin\tsc.cmd --noEmit
.\node_modules\.bin\next.cmd build
```

说明：
- `--ignore-scripts` 用于避开部分 Windows 环境下 pnpm 对 `sharp` 构建脚本的交互审批。
- 真正发布前仍应确认普通 `corepack pnpm install` 能在目标环境运行。

### Step 4：实现最小可用功能

实现时只做当前任务需要的最小改动。

不允许：
- 顺手大规模重构。
- 同一个 PR 同时做多个独立功能。
- 把未实现能力写成已实现。

允许：
- 为完成当前功能拆小文件。
- 为当前功能补充必要类型。
- 修正直接影响当前功能的明显缺陷。

### Step 5：本地演示验证

启动：

```bash
corepack pnpm dev
```

打开：

```text
http://localhost:3000
```

基础检查：
- 页面能正常打开。
- 首屏无明显布局错乱。
- 浏览器控制台无关键错误。
- 当前功能按 README 或 PR 描述中的步骤可复现。

### Step 6：更新文档

需要更新：
- README：运行方式、演示流程、当前能力、差距说明。
- 开发流程文档：只有流程变化时才更新。
- 需求说明书：只有需求本身变化时才更新。

文档要求：
- 只写真实可用能力。
- 未完成能力写入“当前差距”或“下一步”。
- PR 描述和 README 不能互相矛盾。

### Step 7：提交与 PR

提交前检查：

```bash
git status -sb
git diff --check
```

只暂存当前任务相关文件：

```bash
git add <file-1> <file-2>
git commit -m "<message>"
git push -u origin <branch>
```

创建 draft PR：

```bash
gh pr create --draft --base main --head <branch> --title "[codex] <title>" --body-file <body-file>
```

如果 `gh` 不可用：
- 先安装 GitHub CLI。
- 执行 `gh auth login` 完成认证。
- 再创建 PR。

## 四、功能路线图与任务拆分

### 阶段 1：补齐创建事件闭环（P0）

目标：

```text
用户说一句自然语言日程，系统识别文本、解析字段、展示确认卡片，用户确认后创建事件并更新日历。
```

任务拆分：

1. **解析结果类型标准化**
   - 修改：`lib/types.ts`
   - 修改：`lib/voice-parser.ts`
   - 产出：统一的 `ParsedCalendarCommand` 类型。
   - 验证：输入多种中文表达，返回稳定字段。

2. **增强本地自然语言解析**
   - 修改：`lib/voice-parser.ts`
   - 支持：
     - `明天下午3点开会`
     - `下周一上午10点和张三讨论预算`
     - `5月31号晚上8点提醒我交材料`
     - `后天下午两点半开项目会`
   - 验证：为解析函数补测试或编写临时验证脚本。

3. **新增确认卡片**
   - 创建：`components/command-confirmation.tsx`
   - 修改：`components/voice-calendar.tsx`
   - 功能：
     - 展示识别原文。
     - 展示标题、日期、开始时间、结束时间。
     - 支持确认、取消、手动编辑。
   - 验证：语音或模拟文本触发后，不直接创建事件，必须先确认。

4. **新增文字输入兜底**
   - 修改：`components/voice-control.tsx`
   - 功能：
     - 用户可手动输入自然语言命令。
     - 点击解析后走同一套确认卡片。
   - 验证：浏览器不支持语音时仍能演示核心流程。

5. **创建事件后更新视图**
   - 修改：`components/voice-calendar.tsx`
   - 修改：`lib/use-calendar-events.ts`
   - 功能：
     - 确认创建后写入事件。
     - 自动跳转到事件日期。
     - 右侧事件列表立即刷新。
   - 验证：添加明天事件后，右侧显示明天并出现新事件。

### 阶段 2：本地持久化（P0）

目标：

```text
用户新增或删除事件后，刷新页面仍保留日程数据。
```

任务拆分：

1. **事件序列化与反序列化**
   - 修改：`lib/use-calendar-events.ts`
   - 功能：将 `Date` 字段安全存取为 ISO 字符串。

2. **localStorage 存储**
   - 修改：`lib/use-calendar-events.ts`
   - 功能：
     - 初始化时读取本地事件。
     - 增删事件后写回本地。
     - 本地无数据时使用默认示例数据。

3. **重置演示数据**
   - 修改：`components/event-panel.tsx` 或新增设置入口。
   - 功能：允许演示前恢复默认示例数据。

### 阶段 3：提醒能力（P1）

目标：

```text
事件到提醒时间时，页面内提示用户；浏览器允许时发送系统通知。
```

任务拆分：

1. **扩展事件模型**
   - 修改：`lib/types.ts`
   - 字段：
     - `remindBeforeMinutes`
     - `remindedAt`

2. **提醒调度 hook**
   - 创建：`lib/use-reminder-scheduler.ts`
   - 功能：
     - `setInterval` 定期扫描未来事件。
     - 避免同一事件重复提醒。

3. **页面内提醒**
   - 使用：现有 toast 或 sonner 组件。
   - 功能：提醒触发时展示事件标题和时间。

4. **浏览器通知**
   - 使用：Notification API。
   - 功能：
     - 用户授权后发送系统通知。
     - 未授权时保留页面内提醒。

### 阶段 4：删除、查询和编辑增强（P1）

目标：

```text
让语音删除、查询、编辑更接近真实日历助手。
```

任务拆分：

1. **删除候选确认**
   - 语音删除时先列出匹配事件。
   - 用户选择后再删除。

2. **查询范围增强**
   - 支持今天、明天、本周、下周、本月。
   - 查询后切换对应视图。

3. **语音编辑事件**
   - 支持“把明天上午会议改到下午3点”。
   - 先实现候选匹配和确认，再执行修改。

### 阶段 5：LLM/ASR 增强（P2 或后续）

目标：

```text
在本地规则闭环稳定后，引入外部服务提升复杂中文表达解析能力。
```

任务拆分：

1. **抽象解析接口**
   - 创建：`lib/calendar-command-parser.ts`
   - 本地规则和远程 LLM 使用同一返回结构。

2. **新增服务端 API 路由**
   - 创建：`app/api/parse-command/route.ts`
   - 隐藏 API key，不在浏览器直接调用大模型。

3. **接入 DeepSeek 或其他 LLM**
   - 输入：识别文本、当前日期、现有事件上下文。
   - 输出：结构化日历命令。

4. **失败回退**
   - 远程解析失败时回退本地规则。
   - 保证 demo 不依赖外部服务稳定性。

## 五、每个 PR 的最小验收标准

### 文档 PR

- 只改文档。
- `git diff --check` 通过。
- PR 描述说明文档用途和影响范围。

### UI PR

- 页面能启动。
- 桌面宽度下无明显重叠或溢出。
- 关键交互可手动复现。
- README 中演示流程同步更新。

### 解析逻辑 PR

- 有明确输入输出样例。
- 覆盖常见中文日期和时间表达。
- 不破坏已有语音添加、删除、查看命令。

### 存储 PR

- 刷新页面后数据仍存在。
- 能处理旧数据或空数据。
- 不因 localStorage 不可用导致页面崩溃。

### 提醒 PR

- 能触发页面内提醒。
- 能避免重复提醒。
- 浏览器通知权限被拒绝时仍能正常运行。

## 六、当前推荐的下一个 PR

建议下一个 PR：

```text
[codex] Add command confirmation flow
```

范围：
- 新增确认卡片。
- 统一语音识别和文字输入后的解析流程。
- 用户确认后再创建事件。

不包含：
- localStorage。
- 浏览器提醒。
- DeepSeek API。
- 语音编辑事件。

原因：
- 这是“自然语言语音输入，自动解析并创建日历事件”的核心闭环。
- 没有确认环节时，误识别会直接写入错误事件，演示风险较高。
- 完成后再做持久化和提醒，边界更清楚。

每次开发前：

- [ ] 确认任务目标和不做事项。
- [ ] 确认要修改的文件列表。
- [ ] 确认验证方式。

开发中：

- [ ] 小步修改。
- [ ] 不混入无关重构。
- [ ] 不覆盖用户已有改动。
- [ ] UI 文案与实际能力一致。

提交前：

- [ ] `git status -sb`
- [ ] `git diff --check`
- [ ] `.\node_modules\.bin\tsc.cmd --noEmit`
- [ ] `.\node_modules\.bin\next.cmd build`
- [ ] README 或 PR 描述已更新。

PR 前：

- [ ] 分支已推送。
- [ ] PR 标题符合 `[codex] ...`。
- [ ] PR 描述包含功能描述、实现思路、测试方式。
- [ ] Draft PR 已创建。
